# خطة تنفيذ — الحلقة اليومية (Daily Loop)

**التاريخ:** 2026-11-02
**المرجع:** `docs/superpowers/specs/2026-11-02-daily-loop-design.md`
**الستاك:** NestJS 11 + React 19 + PostgreSQL + Prisma + Redis/BullMQ

---

## 0. نظرة عامة

### 0.1 النهج
تنفيذ **رأسي** (vertical slices): كل مرحلة تطلع شغالة من الداتابيز للواجهة، ومختبرة، وقابلة للاستخدام. مفيش مرحلة "بنية تحتية بحتة" بتطول بدون قيمة ظاهرة.

الترتيب مبني **من النتيجة للخلف**: النتيجة هي تجربة حقيقية لحلقة واحدة (حضانة، فصل، أسبوعان). كل ما لا تحتاجه التجربة (الصحة الكاملة، التقييم، الجواز، التقويم) يُبنى بعدها بحسب ما تُظهره.

### 0.3 تعريف "منتهي" (Definition of Done)
أي مهمة تعتبر منتهية فقط لو:
1. منطق العمل مغطى باختبارات وحدة.
2. المسار الحرج مغطى باختبار تكامل.
3. الصلاحيات متختبرة (إيجابي وسلبي).
4. الواجهة فيها حالات: تحميل، فراغ، خطأ.
5. الـ audit event متسجل للأفعال الحساسة.
6. typecheck + lint نضيفين.
7. النص العربي مراجع (مفيش Lorem Ipsum).

## 1. المرحلة 0 — نموذج تفاعلي واختبار المعلمات

**الهدف:** إثبات الفرضية التي يقوم عليها المنتج (معلمة تسلّم فصل 20 طفلاً في أقل من 5 دقائق) قبل بناء أي شيء خلفها.

### المهام
1. نموذج تفاعلي (Figma أو صفحة React ببيانات وهمية) لشاشة الفصل: «الكل حاضر»، الأزرار الجماعية، الاستثناءات الفردية، التسليم.
2. نموذج لشاشة ولي الأمر (ورقة اليوم) وشاشة الاستقبال (مسح الحضور والاستلام).
3. اختبار مع 3 معلمات على الأقل من الحضانة الشريكة بفصل وهمي من 20 طفلاً، وقياس الزمن.
4. تسجيل الملاحظات وتعديل التصميم وإعادة الاختبار عند الحاجة.

### معايير الخروج
- متوسط الزمن < 5 دقائق وبدون شرح متكرر.
- لو فشل → إعادة تصميم وإعادة اختبار قبل بدء المرحلة 2.

**ملاحظة:** المرحلة 1 (التأسيس) لا تعتمد على التصميم ويمكن تنفيذها بالتوازي.

## 2. المرحلة 1 — التأسيس

**الهدف:** مستودع يبني، يشغل، ويتختبر بأمر واحد.

### المهام
1. **Monorepo:** npm workspaces + Turborepo، وضبط `tsconfig` مشترك و`eslint`/`prettier`.
2. **Docker compose:** PostgreSQL 16، Redis 7، MinIO (تخزين محلي بديل S3).
3. **NestJS bootstrap:** config module (env validated by Zod)، global validation pipe، موحد لشكل الأخطاء `{ code, message, details, requestId }`، structured logging، `/health`.
4. **Prisma:** schema أولي، migration workflow، seed لحضانة تجريبية + مستخدمين لكل دور.
5. **React bootstrap:** Vite + React Router + TanStack Query + Tailwind + shadcn/ui + `dir="rtl"` + خط عربي.
6. **`packages/shared`:** Zod schemas للأخطاء والأدوار والصلاحيات وثوابت النطاق.
7. **Auth skeleton:** JWT access (15 دقيقة) + refresh rotation (30 يوم) + argon2 + guards + `@CurrentUser()`.
8. **CI:** lint + typecheck + unit + integration (Postgres service) + migration check.
9. **Observability:** request-id middleware، log correlation، Sentry (اختياري).

### معايير الخروج
- `npm run dev` يشغل API + Web + DB.
- تسجيل دخول تجريبي لكل دور يعمل.
- CI أخضر على أول PR.
- `shared` package يمنع بناء واجهة بعقد API مختلف.

**المخاطر:** الإفراط في إعداد الأدوات. الحد: مفيش إضافات infra غير المذكورة.

## 3. المرحلة 2 — الهوية والعزل

**الهدف:** حساب آمن، طفل بهوية عالمية، وعزل مستأجرين مثبت بالاختبار.

### المهام
0. **هيكل اختبار RLS مشترك (أولاً، قبل أي جدول محمي):** fixture يبني حضانتين وفصلين، معلمة ومعلمة بديلة، ولي أمر بطفل واحد في حضانتين، وطفلاً غير مرتبط به. يشغّل على أي جدول محمي مساري الحضانة وولي الأمر، ويتحقق من فشل القراءة والكتابة عبر الحدود (404) ومن أن دور التطبيق لا يتجاوز RLS. كل جدول جديد يُسجَّل فيه ولا يُدمج بدونه.
1. **`identity`:** `users`, `user_profiles`, `otp_codes`، تسجيل بالموبايل، OTP (مزود حقيقي في staging، كود ثابت في dev)، rate limiting، جلسات وأجهزة.
2. **التشفير:** خدمة `NationalIdService` (AES-256-GCM + HMAC-SHA256 بمفتاح منفصل)، تحقق من الصيغة (14 رقم + checksum)، تقنيع، وتسجيل كل اطلاع كامل.
3. **`children`:** CRUD، ربط ولي الأمر، `children.verification_status` (توثيق الهوية العالمية فقط)، و`origin`. رد **عام** عند تكرار الرقم القومي دون كشف أن الطفل مسجّل لدى جهة أخرى.
4. **`guardian_links`:** دعوة ولي أمر ثانوي، قبول، صلاحيات، إلغاء.
5. **`consents`:** تسجيل/إلغاء، وإصدار موافقة.
6. **العزل بمسارين:**
   - مسار الحضانة: RLS على `nursery_id` + `TenantContext` + Prisma extension ترفض أي استعلام بدون سياق.
   - مسار ولي الأمر: سياسة على `child_id` عبر `guardian_links` النشطة (طفل واحد عبر أكثر من حضانة).
   - دور DB للتطبيق ليس مالك الجداول وبدون `BYPASSRLS`، مع `FORCE ROW LEVEL SECURITY`.
7. **الصلاحيات:** `CapabilityGuard` + مصفوفة الأدوار من المواصفة، مع اختبارات سلبية.
8. **`tenancy`:** إنشاء حضانة بواسطة `super_admin`/`moderator`، تعطيل/تفعيل، إعدادات أساسية، و`classroom_staff` (ربط المعلمات بالفصول بتواريخ بدء/انتهاء) مع دعم المستخدم الواحد في أكثر من سياق (موظف في حضانتين، أو موظف وولي أمر).
9. **`audit`:** خدمة `AuditService.record()` + جدول + سياسة "append only" (revoke update/delete على مستوى DB) + **redaction**: لا رقم قومي ولا تفاصيل صحية خاماً في `before/after` (قائمة حقول متغيرة أو hash).

### الاختبارات الإلزامية
- تشفير/فك تشفير + رفض رقم مكرر (hash).
- تسجيل OTP: صحيح، منتهي، محاولات مفرطة.
- ولي أمر يحاول الوصول لطفل غيره → 404.
- ولي أمر يقرأ طفله من حضانتين → ينجح عبر مسار ولي الأمر.
- دور التطبيق لا يتجاوز RLS (اختبار على الجداول المحمية).
- رقم قومي مكرر → رد عام لا يكشف الوجود.
- معلمة بديلة تظهر لها بيانات الفصل فقط خلال فترة `classroom_staff`.
- معلمة تحاول الوصول لحضانة أخرى → 404 (مش 403).
- تعديل سجل audit مرفوض على مستوى قاعدة البيانات.

### معايير الخروج
- أب يسجل، يضيف طفل، ويشوفه في قائمته.
- حضانتان في نفس القاعدة، وكل واحدة لا ترى الأخرى (اختبار آلي).
- كل فعل حساس له audit event.

## 4. المرحلة 3 — التسجيل والانضمام

**الهدف:** الطفل يدخل الحضانة بمسار موثّق، سواء جاء من الأب أو من الحضانة.

### المهام
1. **`enrollment`:** `enrollment_applications` + `enrollments` + `classrooms`.
2. **مسار الأب:** اختيار حضانة → طلب → حالة الطلب + إشعار.
3. **مسار الحضانة:** مراجعة الطلب، التحقق من الرقم القومي وشهادة الميلاد، موافقة/رفض بسبب، تعيين فصل.
4. **الاستيراد:** قالب Excel + تحقق صف بصف + تقرير أخطاء قابل للتنزيل + معاينة قبل الحفظ.
5. **الدعوات:** توليد دعوة لولي الأمر، صفحة تفعيل، وربط الحساب بالطفل.
6. **الرؤية التشغيلية:** الاستيراد والتسجيل المباشر ينشئان `enrollment` نشطاً بتصديق الحضانة (`attested_by_staff_id`)، فيظهر الطفل للمعلمات فوراً. طلب الأب لا يظهر قبل موافقة الحضانة. `verification_status = unverified` يقيّد الجواز والمشاركة فقط.
7. **الانتقال:** إغلاق تسجيل (`transferred`) وفتح طلب جديد.
8. **Claim والدمج (F9):** الأب المدعو يطالب بسجل طفله بعد OTP، طلب دمج من المدير بموافقة الأب، واعتراض على رقم قومي خاطئ.
9. **مستندات التحقق:** صور شهادات الميلاد في التخزين مع حذف تلقائي بعد اكتمال التحقق (افتراضي ٣٠ يوماً).

### الاختبارات
- طلب → موافقة → `active` (مسار كامل).
- رفض → سبب إجباري.
- استيراد 100 صف مع 5 أخطاء → 95 محفوظ و5 في التقرير.
- طلب لم يوافق عليه لا يظهر في استعلام المعلمة؛ وطفل مستورد ومصدَّق يظهر فوراً قبل تفعيل الأب.
- دمج سجلين لنفس الطفل بعد موافقة الأب، ورفضه بدونها.
- محاولة تسجيل نفس الطفل في نفس الحضانة مرتين → منع.

### معايير الخروج
- حضانة تقدر تدخل 50 طفلاً موجوداً في أقل من 30 دقيقة (استيراد + دعوات)، ويبدأ العمل عليهم في نفس اليوم دون انتظار تفعيل الأهالي.
- كل موافقة/رفض لها audit مع الفاعل والوقت.

## 5. المرحلة 4 — التقرير اليومي

**الهدف:** المعلمة تسلّم فصل 20 طفلاً في أقل من 5 دقائق.

### المهام
1. **شاشة الفصل:** قائمة أطفال + «الكل حاضر» + أزرار جماعية (وجبة/نوم/مزاج) + استثناءات فردية.
2. **القوالب:** `infant` / `toddler` / `preschool` بحقول مختلفة حسب العمر.
3. **الحفظ التلقائي:** مسودة كل 10 ثوانٍ + عند مغادرة الصفحة + استرجاع بعد انقطاع.
4. **التسليم:** تحقق من اكتمال الحقول الإلزامية، `submitted`, إصدار إشعار واحد للفصل.
5. **الاعتماد:** `behavior_note` بحالة `pending_review` → اعتماد/رفض المدير.
6. **التعديل:** المعلمة حتى نهاية يوم التقرير بسبب إجباري، وبعدها المدير فقط؛ `amended` + diff محفوظ.
7. **واجهة الأب:** ورقة اليوم، الفرق عند التعديل، تعليق، ومرفقات لاحقاً.
8. **قياس محلي:** تتبع زمن التسليم في dev لإثبات مقياس النجاح.
9. **العمل دون اتصال:** تخزين محلي (IndexedDB عبر service worker) للمسودة والتسليم المؤجل، مزامنة عند العودة، وسياسة تعارض (آخر تعديل لنفس الحقل مع تنبيه).
10. **بانر الحساسية البسيط:** قراءة `health_profiles.allergies` (إدخال من المدير/الاستقبال) وعرضها بالأحمر في شاشة الفصل، بدون بقية الملف الصحي.

### الاختبارات
- batch 20 طفل في طلب واحد.
- سلوك غير معتمد لا يظهر للأب.
- تعديل بعد النشر يعرض diff.
- استرجاع مسودة بعد إغلاق المتصفح.
- تسليم أثناء انقطاع الإنترنت ثم مزامنة دون تكرار.
- معلمة تعدّل بعد التسليم في نفس اليوم: تنجح بسبب مسجّل؛ في اليوم التالي: مرفوضة.
- صلاحية: معلمة فصل آخر لا ترى الشاشة.

### معايير الخروج
- **اختبار قابلية استخدام ثانٍ على الشاشة المبنية فعلاً** مع نفس المعلمات (الأول كان على النموذج في المرحلة 0): < 5 دقائق وبدون شرح متكرر.
- لو فشل الاختبار → توقف وأعد تصميم الشاشة قبل أي مرحلة تالية.

## 6. المرحلة 5 — الإشعارات

**الهدف:** إشعار يصل، أو يظهر بديل موثوق.

### المهام
1. `push_subscriptions` + VAPID + service worker.
2. قوالب إشعارات عربية + متغيرات.
3. قواعد: quiet hours، تجميع التقرير، أولويات.
4. In-app inbox + badge + حالة مقروء.
5. Retry 3 مرات + سجل تسليم + تنظيف اشتراكات منتهية.
6. شاشة تثبيت PWA (iOS) + تفسير الفائدة.
7. إعدادات إشعار لكل مستخدم (ما عدا الإصابات والاستلام).

### الاختبارات
- إشعار أثناء quiet hours يؤجل (ما عدا الطوارئ).
- فشل الإرسال يظهر في inbox.
- إلغاء اشتراك نوع لا يوقف الإصابات.
- subscription منتهي يُعلَّم expired.

### معايير الخروج
- إشعار حضور يظهر على Android وiOS (مثبت PWA) في staging.
- كل إشعار له سجل تسليم.

## 7. المرحلة 6 — الحضور والاستلام

**الهدف:** حركة الدخول والخروج موثّقة، والاستلام بموافقة صريحة.

### المهام
1. **`attendance_events`:** append-only، `idempotency_key`، دالة `checkIn/checkOut` بقواعد صارمة (مفيش خروج بدون دخول، ومفيش حدثين متتاليين نفس النوع).
2. **QR الطفل:** توليد token 128-bit، تخزين hash، بطاقة قابلة للطباعة، وإعادة توليد عند الفقدان.
3. **شاشة المسح:** كاميرا المتصفح (`BarcodeDetector` مع fallback مكتبة) + إدخال يدوي للكود.
4. **`pickup_passes` + `pickup_pass_children`:** إنشاء من ولي الأمر لطفل أو أكثر (الإخوة)، صلاحية افتراضية حتى نهاية اليوم، PIN 6 أرقام. الرابط والـ PIN يُعرضان **منفصلين** مع تنبيه لإرسالهما برسالتين.
5. **QR ولي الأمر الدائم (`guardian_credentials`):** للاستلام بنفسه دون تصريح، مع تدوير عند الفقد، ولا يعمل لولي أمر `restricted`.
6. **التحقق:** endpoint واحد يرجع سبب الرفض بوضوح (منتهي، مستخدم، ملغي، PIN خطأ، خارج الفصل). عند الاستلام بتصريح تعرض الشاشة اسم المستلم وصلته، ولا يتم الاستلام قبل تأكيد الموظف مطابقة الهوية (`receiver_id_checked`).
7. **الاستلام اليدوي:** للمدير فقط + سبب إجباري + audit.
8. **لوحة اليوم:** من حاضر الآن، من خرج، من متأخر.

### الاختبارات
- مسح مزدوج في ثانية → حدث واحد.
- تصريح واحد لطفلين: استخدامه يسجّل خروجاً لكليهما، ولا يعمل لطفل غير مدرج.
- QR ولي الأمر: ينجح لولي نشط، ويفشل لـ`restricted` أو `revoked`.
- تصريح بدون تأكيد مطابقة الهوية → مرفوض.
- خروج بدون دخول → مرفوض.
- تصريح منتهي/مستخدم/ملغي → مرفوض بسبب صحيح.
- 6 محاولات PIN خاطئة → قفل مؤقت + تنبيه.
- معلمة تحاول تسجيل حضور لطفل خارج فصلها → 403.

### معايير الخروج
- مسح الحضور ≤ 3 ثوانٍ من فتح الشاشة.
- كل استلام مرتبط بتصريح أو QR ولي أمر أو استثناء مدير مسجّل.

## 8. المرحلة 7 — التجهيز والتجربة

**الهدف:** حضانة شريكة تقدر تشتغل أسبوعاً كاملاً بدون تدخل.

### المهام
1. **Onboarding wizard:** إعداد الحضانة، الفصول، استيراد، دعوات.
2. **بيانات تجريبية:** حضانة كاملة ببيانات واقعية للعرض والاختبار.
3. **مراجعة النصوص:** كل رسالة خطأ مفهومة بالعربي، مفيش مصطلحات تقنية.
4. **حالات الفراغ:** كل شاشة لها حالة فراغ مفيدة.
5. **الأداء:** قياس شاشة الفصل على 3G مصطنع + تحسين الاستعلامات.
6أ. **الامتثال القانوني (شرط قبل أي بيانات حقيقية):** مراجعة قانون حماية البيانات الشخصية (151/2020) مع محامٍ متخصص وتحديد متطلبات الترخيص/التسجيل ومكان التخزين.
6. **الأمان:** مراجعة قائمة OWASP الأساسية، rate limits، رؤوس أمان، مراجعة صلاحيات.
7. **التشغيل:** نسخ احتياطي، استرجاع، runbook، مراقبة أخطاء.
8. **التجربة:** حضانة واحدة، فصل واحد، أسبوعان، مع قياس:
   - زمن التقرير
   - نسبة الفصول المسلَّمة قبل 18:00
   - فتح الأهالي
   - الاستلام الموثّق (QR ولي أمر أو تصريح)
9. **قرار المتابعة:** نكمل، نعدّل، أو نعيد تصميم الشاشة. وخلال التجربة تستمر الحضانة في إجراء الإصابات المعتاد (ورقي/واتساب) ويُعلَن ذلك للأهالي.

### معايير الخروج
- 5 أيام متتالية بدون خطأ حاجب.
- مقاييس النجاح من المواصفة مقاسة وموثقة.
- ملاحظات المعلمات والأهالي مجموعة ومصنّفة.
- المراجعة القانونية مكتملة قبل بدء التجربة.

## 9. المرحلة 8 — الصحة والإصابات الكاملة

**الهدف:** معلومات السلامة ظاهرة، والإصابات موثّقة ومقرّة.

### المهام
1. `health_profiles`: حساسية، أمراض مزمنة، أدوية، طوارئ.
2. بانر أحمر في شاشة الفصل + في بطاقة الطفل.
3. `incidents`: إنشاء، وصف، شدة، شهود، إجراء.
4. إشعار فوري + طلب إقرار.
5. مهمة مجدولة للتصعيد بعد ساعتين بدون إقرار.
6. إغلاق الحادث + سجل كامل.
7. صلاحيات: الاستقبال يرى تنبيه الحساسية فقط، لا التفاصيل الطبية.

### الاختبارات
- إقرار يسجل الفاعل والوقت.
- تصعيد يحدث مرة واحدة ولا يتكرر.
- معلمة فصل آخر لا ترى السجل الصحي.
- حساسية تظهر في شاشة الفصل خلال تحميل واحد.

### معايير الخروج
- أي إصابة تُنشأ في أقل من 60 ثانية.
- 100% من الإصابات لها حالة واضحة (open/acknowledged/closed).

## 10. المرحلة 9 — التقييم والجواز

**الهدف:** تقييم معتمد يتراكم، وجواز يُشارك بأمان.

### المهام
1. `assessment_domains` الافتراضية الخمسة + إمكانية تخصيص لاحقاً.
2. مسودة المعلمة → إرسال → اعتماد/رفض المدير → نشر.
3. واجهة الأب: المحاور، الملاحظة العامة، التعليق.
4. **`passport`:** إسقاط (projection) من التقييمات المنشورة + تاريخ التسجيل + الحضور.
5. إنشاء مشاركة: نطاق + مدة 7 أيام + رابط.
6. صفحة عامة للقراءة فقط + تسجيل وصول + إلغاء فوري.
7. تصدير PDF بسيط للجواز (اختياري في هذه المرحلة).

### الاختبارات
- تقييم `draft` لا يظهر للأب.
- رفض يعيد الحالة `draft`.
- رابط منتهي → 410.
- محاولة الوصول لنطاق غير مصرح (صحي) → رفض.
- كل وصول مسجل.

### معايير الخروج
- دورة تقييم كاملة من 3 أدوار.
- رابط جواز يعمل على موبايل بدون تسجيل دخول.
---

## 11. المرحلة 10 — التقويم

**الهدف:** الأنشطة والرحلات بموافقاتها.

### المهام
1. `calendar_events` + عرض شهري/أسبوعي.
2. رحلة → طلب موافقة لكل طفل + حالة الموافقة.
3. إشعار قبل 24 ساعة.
4. صلاحية: المعلمة تنشئ نشاط فصلها، المدير ينشئ عام.

### الاختبارات
- رحلة بدون موافقة لا تظهر كـ "مؤكد".
- إشعار قبل 24 ساعة.
- ولي أمر يرى أنشطة فصل طفله فقط.

## 12. استراتيجية الاختبار المستمرة

| الطبقة | الأداة | ما تُغطيه |
|---|---|---|
| وحدة | Vitest/Jest | آلات الحالة، التشفير، الصلاحيات |
| تكامل | Supertest + Postgres حقيقي | كل endpoint + RLS |
| عقد | Zod schemas | API ↔ Web |
| E2E | Playwright | يوم كامل، استلام، تقرير |
| أمن | اختبارات مخصصة | IDOR، تصاريح، OTP، rate limit |
| أداء | k6 (سيناريو بسيط) | شاشة فصل 20 طفل، مسح حضور متزامن |

**قاعدة:** أي باگ أمني أو في الصلاحيات = اختبار جديد قبل الإصلاح.

## 13. المخاطر أثناء التنفيذ

| الخطر | الإشارة المبكرة | الاستجابة |
|---|---|---|
| شاشة التقرير بطيئة/ثقيلة | اختبار المعلمات يفشل (على النموذج أو على الشاشة) | إعادة تصميم قبل المتابعة |
| RLS تسبب تسريباً | اختبار عزل أحمر | إيقاف الدمج، إصلاح فوري |
| Push لا يعمل على iOS | فشل اختبار staging | إظهار inbox كمسار أساسي + دعم تثبيت |
| الاستيراد يفشل مع ملفات حقيقية | أخطاء صيغة | قبول CSV أيضاً + معاينة |
| المعلمات لا يستخدمن | استخدام منخفض في التجربة | تبسيط + تدريب + إشعارات تذكير |
